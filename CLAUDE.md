# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A native SwiftUI macOS app (macOS 14+, Apple Silicon) that wraps Apple's `container` CLI — a GUI for managing containers, images, machines (Linux VMs), volumes, and builds, in the spirit of Docker Desktop. There is **no** private API or daemon integration: the app shells out to `container ... --format json` and decodes the output.

## Naming note

The project was renamed from **Skipper** to **Container Manager**. Two names are intentionally *not* "Container Manager":

- The Xcode app/module is `Container Manager` / `Container_Manager` (spaces → underscore), set by `project.yml` — the source of truth for the Xcode project (produces `Container Manager.xcodeproj`, scheme `Container Manager`).
- The SwiftPM product/binary is `ContainerUI` (`Package.swift`, `Sources/ContainerUI/`) — unchanged.

Asset files use a space-free `ContainerManager` prefix (`Support/ContainerManager.entitlements`, `Assets/ContainerManager.*`, `Sources/ContainerUI/Resources/ContainerManagerLogo.png`) to avoid shell-quoting pain. When editing, treat `project.yml` as authoritative for Xcode; keep README/scripts in sync with it.

## Build & test

The `.xcodeproj` is **not committed** — it is generated by [XcodeGen](https://github.com/yonaskolb/XcodeGen) from `project.yml`. After cloning or editing `project.yml`:

```bash
xcodegen generate                 # writes "Container Manager.xcodeproj"
```

Two build paths:

```bash
# Full app (signing, assets, tests) — the real target
xcodebuild -project "Container Manager.xcodeproj" -scheme "Container Manager" -configuration Debug build

# Fast Xcode-free iteration (no code signing, no asset catalog)
swift build
swift run ContainerUI
```

Tests (XCTest, via the Xcode project only — not SwiftPM):

```bash
xcodebuild test -project "Container Manager.xcodeproj" -scheme "Container Manager" -destination "platform=macOS"
# single test:
xcodebuild test ... -only-testing:"Container ManagerTests/<Class>/<method>"
```

Test targets: `Container ManagerTests` (unit) and `Container ManagerUITests` (UI). They `@testable import Container_Manager`, which is why the module name must stay `Container_Manager`.

Release (Developer ID + notarization): `./scripts/build-release.sh` (see naming note — currently stale).

## Architecture

Everything the app knows about containers flows through one seam. Layering, top to bottom:

- **`ContainerEngine.swift`** — the only place that touches the `container` CLI. A stateless `struct` of `async` methods, each mapping to a subcommand. Binary path is resolved once (`/opt/homebrew/bin`, `/usr/local/bin`, `/usr/bin`, then `which`). Three process-running strategies, chosen per command:
  - `run(_:)` — one-shot; drains stdout **and** stderr on separate queues to avoid pipe-buffer deadlock. `runJSON` decodes into `Models.swift` types (coerces empty output to `[]`).
  - `runWithPTY(_:)` — for subcommands that reject plain pipes. Notably `machine run`, which does TTY ioctls on stdin; used to boot machines (there is no `machine start`).
  - `stream(_:)` — returns `(Process, AsyncStream<String>)` for live line-by-line output (pull / build / follow logs); caller keeps the `Process` to cancel.

- **`Models.swift`** — `Codable` structs mirroring the CLI's JSON exactly (nested `Configuration`/`Status`, optional-heavy since fields vary by command). Add computed helpers here (`isRunning`, `displayName`, `volumeName`) rather than in views. `CT`-prefixed types = container-tool models.

- **`AppModel.swift`** — `@MainActor ObservableObject`, the single source of UI truth. Holds all `@Published` collections, drives a 4-second auto-refresh loop (`startAutoRefresh`), and funnels every mutation through `perform(_:success:_:)` (run work → refresh → toast/error) or `performMachine(...)` (same, plus per-ID busy-spinner tracking for multi-second VM boots). Views never call `engine` directly — they call `AppModel` methods.

- **`App.swift` + `Views/`** — SwiftUI. `RootView` is the sidebar split view (destinations enumerated in `SidebarItem`) with an engine-offline splash. `Components.swift` holds shared UI (status pills, cards, flow layout, toasts). Feature views (`ContainersView`, `MachinesView`, `ImagesView`, etc.) render `AppModel` state; sheets (`RunSheet`, `PullSheet`, `CreateMachineSheet`, `CreateVolumeSheet`) collect input then call an `AppModel` action. `TerminalSurface`/`ConsoleView` embed SwiftTerm for interactive shells.

Data flow for any user action: **View → AppModel method → ContainerEngine subcommand → decode into Models → published back → auto-refresh reconciles.**

## Dependencies

- **SwiftTerm** (`from: 1.13.0`) — terminal emulator for interactive login shells into machines/containers.

## Resource loading gotcha

`Bundle.module` only exists in SwiftPM builds. The `SWIFTPM_BUILD` compile flag (set in `Package.swift`) selects `Bundle.module` for SwiftPM and falls back to `Bundle.main` for the Xcode app target — relevant when loading bundled resources (e.g. the app logo in `DashboardView`).
